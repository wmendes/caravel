Infrastructure as code for Stellar appchains

Declare a lane.
Plan it.
Apply it.

Caravel turns one lane file into an appchain that settles to Stellar in the token you choose. plan shows every change on Stellar and on your host before it's made, apply makes it, and destroy winds the lane down to an exit proof for every account.

One lane file

Everything about a lane lives in one file.

What the lane is, and where it runs. plan reads Stellar and your host, and apply changes only what differs from the file.

# lanes/perps/config/lane.caravel-perps.testnet.toml (abridged)
[lane]
name = "caravel-perps-testnet-0"
[app]
template = "perps"
[node]
block_time_ms = 1000
checkpoint_every_blocks = 60

[env.testnet]
network = "testnet"
admin = "caravel-admin"  # a key in the keystore
token = "circle-usdc"
settlement = "CBIHBEUZ…PONWO"
threshold = 2

[[env.testnet.validators]]
name = "1"
key = "caravel-validator-1"  # and 2, 3

[env.testnet.host]
provider = "ssh"
transport = "gcloud-iap"
address = "caravel-1"
  1. plan

    Lists every change on Stellar and on your host, down to the settlement contract's address, before anything is sent.

  2. apply

    Deploys the contract, installs the release and starts the nodes. Run it again and nothing changes. Interrupted, it finishes on the next run.

  3. status

    Height, checkpoints on Stellar, when a freeze would become possible, and whether the lane still matches its file.

  4. destroy

    Drains the lane, writes every account's exit proof, and freezes the contract so users withdraw on Stellar.

Configure and plan

Every rule is a line. Every change gets a plan.

Pick what you'd change. plan compares the file with the contract on Stellar and the nodes on your host, and says what apply would do.

How it works

Nodes on your host. Money on Stellar.

The sequencer and every validator run the lane's Soroban Wasm. The token stays in the settlement contract, and every checkpoint is checked there.

Top band: your lane, on your host Bottom band: Stellar
  1. Stellar → lane1 DepositLock the token in the settlement contract. The same amount appears on the lane.
  2. On the lane2 Use itEvery block runs the app: an order book on Perps, transfers on Payments.
  3. Lane → Stellar3 CheckpointValidators sign the new state. It goes to Stellar with its block data, and the contract checks the signatures.
  4. On Stellar4 WithdrawThe token goes back to your wallet, and only against an accepted checkpoint.

Who you trust

Between checkpointsThe validators. They run every block again and sign only what they checked. At each checkpointTheir threshold, checked on Stellar. Anyone can replay the lane from Stellar to check them. If the lane stopsNo one. Anyone can freeze it, and every account withdraws its last checkpointed balance on Stellar.

When it ends: destroy

  1. 1Drain until the last checkpoint is accepted
  2. 2Export every account's exit proof to exit.json
  3. 3Trigger, then wait out the forced-withdrawal window, 1 h on Caravel Perps
  4. 4Freeze so users withdraw on Stellar with their proofs

Testnet software, not audited. A lane's admin can still upgrade its contract and rotate its validators, and Caravel Perps' three validators run on one machine operated by the Caravel team. The token's own rules still apply: an issuer's freeze or clawback reaches the contract's balance too.

# build, then the keys the lane file names
./scripts/build-contracts.sh
cargo build --release -p caravel-cli -p caravel-payments-node

for k in pay-local-admin pay-local-v1 pay-local-v2 \
  pay-local-v3 pay-local-relayer; do stellar keys generate "$k"; done

# the lane
L=lanes/payments/config/lane.caravel-payments.local.toml
./target/release/caravel plan    $L --env local
./target/release/caravel apply   $L --env local
./target/release/caravel destroy $L --env local
